# Pokémon Legends: Arceus (`01001F5010DFA000`)

Update 1.1.1 (`v262144`) over the base game, SDK 11.4.0. Game Freak's engine between Pokémon Sword's ([0100ABF008968000](../0100ABF008968000/README.md)) and the Trinity engine of Pokémon Scarlet and Legends: Z-A, on NVN, with Havok physics, Wwise sound and Pia / NPLN networking. Modules `main`, `subsdk0` (the movie module, which the profile does not load: `main` takes nothing from it the host does not supply), `subsdk1` (GLSLC) and `sdk`; the `sdk` build (`b39add63…`) is Kirby and the Forgotten Land's ([01004D300C5AE000](../01004D300C5AE000/README.md)). Started from the provisional profile the NSP script wrote from its survey (`dm/games/profile_guess.py`). Plays on the Mac at 30 fps, as on the Switch, from the first boot to free movement on the Obsidian Fieldlands beach (a short check, below). An unsigned IPA is built (4.2 GB); iOS is untested.

## Bring-up

- **Resolved: a `Break` in `nninitStartup`** (`Break#1 reason=0` at `sdk+0x39fb54`, from `StandardAllocator::Initialize` at `sdk+0x2f98e4` ← `main+0x2779d8c`). The host's cap lowered the allocator's 32 GB to 4.06 GB, but this `sdk` build aligns a region of 1 GB or more to 1 GB, so the region would have started at alias +1 GB and ended past the 4.38 GB alias region. The SDK-wide node-area patch matched this build (implementation 3), the alignment patch had no implementation for SDK 11.4: its placement helper (`sdk+0x34e1d8`) is the SDK 12.3.9 one with 8 more bytes. It is now the alignment patch's second implementation, and both cuts are registered for this build: a build a profile was brought up on takes only registered cuts, so with this profile in `dm/games` the SDK-wide rules no longer reached it (the `Break` came back once). The region lands at alias +0.06 GB.
- **Resolved: an abort on Metal's compiler queue** a few seconds into the language screen (`[AGX] Failed assertion "error == MTLCompilerErrorNoError"` in `findOrCreateComputeFastClearPipeline`, `MTLCompilerService` crash reports in `AGCLLVMStatelessFragmentObject::buildBlendFactor`), with or without the pipeline prebuild. The pipeline was `ha_post_effects.bnsh` variation 4 (`f4f36a03b0c6691d`): an RGBA16Float target blended with destination factor `SRC1_ALPHA`, the shader writing outputs 0 and 1. A temporary log of each blended attachment in `pso_desc` named it as the last pipeline before the abort. `DM_NVN_DUAL_WANT` then listed a second one, `ff45da02e225f961`, in the first minute.
- `[RED] no render target could get an MTLTexture` once at boot ([Passes with no render target](../../../docs/reference/rendering.md#passes-with-no-render-target)); no other red line on the route below.
- The NSP script's rewrite step was reused after the alignment rule was added: it keyed only the patch files that name one of the modules' builds ([The packing script in detail](../../../docs/development.md#the-packing-script-in-detail)).

## Crash in the capture demo

Open: the cause; the crash is worked around ([GitHub issue #712](https://github.com/seedds/nxnative/issues/712)).

- **Symptom:** `CRASH sig=11 addr=0x118 pc=main+0x16e34fc lr=main+0x16e34ac` on `JobThread2`, x8 = 0, after 37 to 65 minutes of normal play on the Mac, with no `[RED]` line before it. Three reporters; the first lost all three sessions of one day to it. The backtrace is always `main+0x19d244c main+0x1cd25e0 main+0x1cceda8 main+0xace34c main+0x1bd9e9c`, and the last frame takes about 1 ms of GPU time.
- **What the code does:** the capture demo task (`main+0x1ccf1a4`; `bin/demo/graphic/system_resource/capture/ob0201_00/anm/capture_animcfg.tracn`, `ThrowableObject`, `my_poke_ball`) builds a ball object and calls `main+0x19d2368`, which calls `main+0x16e33ec` on a 0x1d0-byte object held at `+0x130` of a 0x2e8-byte owner. That function locks the weak reference at `this+0x88` (`main+0x16e9e98`) and reads `[result + 0x118]` with no check. Two things give a null result: the reference itself is null, or its object is dead. The crash log cannot tell them apart.
- **What was measured:** the object's constructor zeroes `+0x88` (`main+0x18954c4`, frame 4595 on the first load) and the field setup's state 0x18 fills it (`main+0x1877a4c` through `main+0x16dde90`, frame 4648): 53 frames with a null reference in that run. That state runs on whichever thread takes the job: the main thread in that run, `JobThread1` (frame 5548) in another. The part of the task that was read has no check for this. At the crash the main thread and `JobThread1` are parked in the job wait, so nothing else is running on that object at that instant. No host service is on the path.
- **Not established:** which null path the crashes take; whether the owner is rebuilt for each scene (one reporter's single hit was followed by a new scene's textures). The likely reading is an order the game does not enforce between the task's own loading and the field setup, which the host's timing exposes. A fresh save does not reach the path: 9 minutes of the route below never called `main+0x19d2368`.
- **Workaround:** `patches.py` returns the function's empty result (`{0, 0}` through x20) on both null paths, before it takes any reference. All 12 direct reads of the result (the ball's `+0x810`, `main+0x19cbcd0` to `main+0x19d1fac`) null-check it; three other places copy it as a reference (`main+0x19cc230`, `main+0x19d2074`, `main+0x19d257c`), whose users were not followed. The room for the check is two of the function's five identical blocks, so the abort stub stays. It is function-matched on 1.1.1 ([function-matched cuts](../../../docs/reference/rewriter.md#function-matched-cuts-for-unregistered-builds)); other builds are unchecked and get a red line if the function differs.
- **Checked:** the rewriter matches the rule once and writes the five cuts, and the game then boots on the Mac to the field setup with no crash (200 s, on the disk's older shader libraries). The patched function run on the module's own bytes in a small interpreter: both null paths return `{0, 0}` with the stack and callee-saved registers restored, and never reach `main+0x16e34fc`; a live object goes on to `main+0x16e3420` as before. The issue's earlier form of the cuts, with the same effect, ran about 7 hours on the Mac with no crash, and the skip was seen once (id 1, frame 142020, followed by 55 minutes of play). These cuts have not met the path in play, and any visible effect on that one ball is unknown.
- **To settle the cause:** `DM_PROBE=main:16e341c,main:16e3828` on a save with Poké Balls, with `DM_PROBE=main:16dde90` to see the order.

## 60 fps

The game runs at 30 on the Switch. Two things in 1.1.1's `main` hold it there, and the frame step stubs in `patches.py` move both to the host's frame step ([`fps_target`](../README.md), the launcher's **Frame rate**):

- **The present interval.** The start-up code builds the display's settings on the stack and the display setup sets the window's present interval to one word of them + 1 (`main+0x2aa2788`). The word is 1 (`main+0x277d838`): interval 2. The stub makes it 0 when the target is not 0.
- **The frame period.** The game steps its time by a stored period, not by the clock: the frame-time object's constructor (`main+0x277bda4`) stores 33,333,334 ns in four pairs, read through a getter (`main+0x278303c`). With the interval at 1 alone the game ran at double speed. The stub in the getter stores the host's step, the vsyncs the frame stays on screen, times 16,666,667 ns: 1/60 s at 60 fps, 1/30 s when the host holds 30 (target 30, heat, a movie, late frames).
- **Target 0** keeps the game's own interval 2 and period. It is the profile's `fps_target`, so the Mac and iOS run at 30 as before; Android's default is 60 ([`android_defaults.txt`](android_defaults.txt)), and 60 has not been run on the Mac or iOS.
- **Who sets the period:** one function sets the four pairs (`main+0x2781508` to `main+0x27815a4`), each to the table's 33,333,334 ns; no code selects 1/60 or builds 16,666,667 as an immediate. Every reader found (about 50 sites, the scene update at `main+0x279a6f0` among them) reads pair 1. One of them, `main+0x2b4344c`, divides the period by a nominal one from a second table (`main+0x39848d0`), a time scale that follows the step. The scan sees only calls whose pair and table index are immediates.
- **Checked:** on an AYN Odin 3 (Adreno 830, Android 15, 2026-11-10 and 11) in a fork with the same two period stubs and the interval as a fixed cut: 60 fps in play with the host's line `frame step: game time … (1.000 of real time)`, and 1,800 of 1,800 frames at 60 through a scripted camera pan; the interval cut alone ran at double speed. The rewriter places the three stubs on 1.1.1's `main`. On 2026-11-12, the same Odin with this profile's `patches.py` and a freshly rewritten `main` (three stubs, the interval read from the state page), in the fork's host: target 60 ran at 60 fps with `game time 30.02 s in 30.03 s (1.000 of real time)` and 1,800 of 1,800 frames held one vsync; target 30 ran at 30 fps with `game time 60.00 s in 59.99 s (1.000 of real time)`, 1,800 of 1,800 frames held two vsyncs, 11 of them late; target 0 ran at 30 fps (`frame step as the game sets it`), and the view after a scripted 2 s camera turn was the same at targets 0 and 30. Not run: the Mac and iOS, and movies. This repository's own host, and frames that come late at 60 in play, were run on 2026-11-13 on a Galaxy Z Flip 7 (under [Files and shaders](#files-and-shaders)): game time stays within 1% of real time while the host steps between 1 and 2 vsyncs, and falls to 0.96–0.97 only while frames take 3 vsyncs.
- The Odin held 60 through that pan only with its GPU clock kept up (832 MHz); when frames are late the host's hold steps to 30 and the period follows it.
- **The Android hand runs** of 2026-11-12 (v0.8.2, under [Files and shaders](#files-and-shaders)) predate the 60 fps default: the game ran at its own 30, Android's target then. The 2026-11-13 run on the Galaxy Z Flip 7 is at the 60 default: the beach stretch holds Playable – major issues (median 34.2), Jubilife doesn't (median 25.1), and no stretch of play holds 60.

## Title screen freeze

Resolved (a workaround in the game's code, whose race is the cause; 2026-11-14).

- **Symptom:** on a OnePlus Pad 3 (Adreno 830) at the 60 fps default, the idle "Press A" title stops 35 to 65 s after the start in some starts, before any input: no frames, sound goes on, no `[RED]` line, the frame step at hold 1 to the last trace row. A check on 2026-11-13 saw it in 2 of the 6 starts of v0.8.10 (a72a85c5; one with `DM_VK_SLOT0_FILL=0`, so not #482) and 0 of one start each on two older builds; on 2026-11-14, 1 of 20 starts of the same code.
- **What the thread dump shows** (`DM_CTL` `dump` at the freeze, twice, 16 s apart, with no CPU time or SVC moving in between): every guest thread in a condition wait with its mutex free, and the NVN queue replay, the completion thread and the present path idle. `RenderWorker` (priority 40, core 0) waits in the fork/join at `main+0x2ac2c98` for the join's count to be 1; the count (`+0x138` of the join, the word 8 bytes past the mutex word it waits on) is 0 and its done flag 0. `JobThread1`, which handed it the job, waits for that flag (`main+0x2ac1b10`); the main thread and `JobThread2` wait in the job system behind it (`main+0x296d9a4`).
- **Cause:** the render job system's fork/join, in the game's code. The dispatcher sets the count to 1 under the join's mutex and hands the leader job to core 0's render worker. The leader counts each of its two helper jobs (the other cores' render workers) with a plain `ldr` / `add` / `str` outside the mutex, then does its share and waits under the mutex for the count to come back to 1; each helper subtracts one under the mutex when its share is done, and the leader's own last subtraction brings it to 0 for the next dispatch. A helper's subtraction that lands between the leader's load and store of its second count loses one of the two updates: the count ends at 0 (the leader's add lost, as in the dump) or 2, and the leader never sees 1. On the Switch a woken helper starts only after the leader's unlock SVC and a wake on another core, while the leader's count is a few instructions after that SVC; on the host every guest thread is a host thread that can be preempted, moved or held by a page fault between any two instructions. Which of these opens the window on the Pad 3 was not measured.
- **Workaround:** `patches.py` `join_count` makes each of the seven updates (the four counts and the leader's last subtraction in `main+0x2ac2460`, the subtraction in each helper, `main+0x2ac2f64` and `main+0x2ac3038`) one `stadd` of +1 or −1 to the word ([A fork/join count updated outside its mutex loses an update](../../../docs/reference/threads.md#a-forkjoin-count-updated-outside-its-mutex-loses-an-update)). Function-matched, three functions that apply together; other builds are unchecked.
- **Checked** on the Pad 3, the same host (a72a85c5 with a thread-dump diagnostic) and game files, only `main`'s rewrite swapped, idle at the title with no input:

  | `main` | Setting | Starts | Froze |
  |---|---|---|---|
  | a72a85c5's rewrite | the 60 fps default, 90 s idle | 20 | 1 (about 62 s after the start, the dump above) |
  | with the cuts | the 60 fps default, 90 s idle | 20 | 0 |
  | a72a85c5's rewrite | `DM_FPS_TARGET=0` (the game's own interval 2, 30 fps, as before #330), 125 s idle | 12 | 0 |
  | a72a85c5's rewrite / with the cuts | four busy shell loops beside the game, 300 s idle | 2 / 2 | 0 / 0 |
  | a72a85c5's rewrite + a ~1 ms spin inside the leader's second count (diagnostic) | the 60 fps default | 4 | 4, at the first frame: the same wait, the count **2** in the three dumped (the helper's subtraction lost) |
  | with the cuts + the same spin before the `stadd` | the 60 fps default | 6 | 0, the title at 60 (frame time p50 16.69 ms) |

  The natural rate on these starts was too low for the first two rows alone to tell the cuts from chance; the spin makes the race happen at every start without them and never with them. With the cuts every title start of the table held one vsync to its last frame-step row.
- **Frame rate with the cuts** (one start each, from a save: A at the title, then 150 s with no input): the title held 60 in every start above. On the beach both rewrites held 60, the last 1,800 frames all at hold 1 (frame time p50 16.7 ms, game time 1.000 of real time). In Jubilife at night both stepped to hold 2 (90% and 87% of the last 1,800 frames, the rest at 3), with a frame time p50 of 35.3 and 36.2 ms. The cuts change no frame rate.
